| 2 | `EmployeeIn` fields | Employee codes, names, emails and departments lacked contract validation. | Submit `emp_code="ABC"`, an empty name/department, an invalid email, or overlong text; these should return 422. | Added the contract's patterns and length limits using Pydantic fields. |

| 5 | `create_employee()` and app startup | Check-then-insert allowed concurrent requests to create duplicate employee codes; no unique index enforced the requirement. | Send 8 simultaneous creates for the same code: exactly one must return 201, the others 409, with one stored document. | Create a unique `emp_code` index at startup and catch `DuplicateKeyError` on insert instead of relying on a prior lookup. | 10 | `create_employee()` creation time | Used a naive local datetime, which PyMongo treats as UTC, shifting the stored instant on non-UTC hosts. | Freeze the server clock and create an employee; the stored time must represent that exact UTC instant with whole-second precision. | Use timezone-aware UTC now and truncate microseconds before storing. |
| 11 | Employee create/list responses | Returned datetimes as strings rather than integer epoch milliseconds. | Check both responses and a seeded naive UTC datetime; `created_at` must be an integer with the correct instant regardless of the host timezone. | Share an employee serializer that converts datetime to integer milliseconds, treats naive database datetimes as UTC, omits `_id`, and leaves stored BSON dates unchanged. |

| 14 | `punch_in()` employee lookup | Dereferenced a missing employee, producing a server error. | Punch in with an unknown employee code; expect 404 and no attendance write. | Check for a missing employee immediately after lookup and raise HTTPException 404. |
| 15 | `punch_in()` timestamp conversion | Used the host timezone and retained milliseconds, changing attendance dates and violating whole-second precision. | Use the same epoch on UTC and non-UTC hosts, including 09:40:00.900 IST; stored UTC instants must agree and have no fractional second. | Convert integer whole seconds explicitly to aware UTC; normalize calculation inputs to whole-second UTC. |
| 16 | `punch_in()` attendance date | Used the instant's local calendar date without IST or overnight shift rules. | For a 22:00-06:00 shift, 7 July 02:00 belongs to 6 July; exactly 06:00 belongs to 7 July. | Derive the IST date and move to the previous day only for overnight punch-ins strictly before shift end. |
| 17 | `compute_late_minutes()` | Floored minutes before checking grace and anchored shift start to the punch's day/timezone. | A 09:30 shift punched at 09:40:01 must give 10 late minutes; an overnight 02:00 punch against the prior day's 22:00 start gives 240. | Anchor shift start to the attendance date in IST, compare elapsed seconds to 600, then floor minutes from shift start. |

## Final verification — 12 October 2026

Used isolated temporary databases and separate test servers. The supplied sample database was not modified. Test databases were dropped and test servers stopped afterward.

- Loaded 100,000 attendance records and 570 employees, including 50 mid-month no-log joiners and 20 future joiners. Started with only MongoDB's default indexes, so application startup created every required index.
- Compared listing pages and employee, department, leaderboard and 92-day trend results against independently calculated expectations.
- Checked eight explain variants across all five supported operations: IXSCAN present, COLLSCAN absent, and reported nested collectionScans equal to zero.
- Exercised eight-way HTTP races for employee creation, punch-in and punch-out. Each produced exactly one successful request; conflicts returned 409. The separate correction regression forced eight requests to read the same snapshot, yielding one 200 and seven 409 with one audit entry.
- Completed an HTTP create → punch-in → punch-out → correction → listing → monthly-report workflow, and verified unavailable-database health handling returns 503.
- Reran correction, monthly, department-summary, leaderboard, trend and explain regression suites against MongoDB 7.0.26, using a clean Git archive and a fresh virtual environment with requirements installed from scratch. Also checked the existing environment against MongoDB 8.2.7. Python was 3.14.4 in both runs; Python 3.11 itself was not separately executed.
